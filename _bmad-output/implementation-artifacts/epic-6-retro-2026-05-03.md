## What Went Well

**Scope discipline was consistent.**
Every story stayed narrowly scoped to its stated usability refinement. No scope creep, no unplanned refactors.

**Story 6.7 transactional architecture was solid.**
Move/swap between days had real hidden complexity — payments, images, and feedback all attach to `dayPlanItemId`, not to the day. The decision to reassign `tripDayId` transactionally instead of delete-and-recreate preserved item identity and avoided cascade bugs across related entities.

**UX consistency work surfaced a latent bug.**
Story 6.6 (aligning day-item photos with accommodation photos) forced a direct comparison of the two dialog implementations. Code review caught that the two had different CSRF token fetch behavior — accommodations fetched on-demand, day items were silently failing when the initial token load missed. The consistency refactor found a real bug that defensive testing alone would not have caught.

**OSRM routing service already existed.**
Story 6.5 (auto-fill travel segments) originally assumed it might need to scrape Google Maps or use an unsupported API. Code analysis found an existing OSRM-backed routing service already in the repo. The story was implemented through a new read-only `route-preview` endpoint backed by that service — no new dependency needed.

**Code review consistently caught real issues.**
5 of 8 stories had review follow-up fixes. Notable catches:
- Compact trigger label regression (6.2)
- 44px minimum touch targets on mobile (6.3)
- Partial-route fallback safety (6.5)
- CSRF token parity between dialog types (6.6)
- Move overwrite confirmation enforced against live server state (6.7)

**Zero new external dependencies.**
Story 6.8 (PDF export) could have introduced `jspdf`, `puppeteer`, or `html2canvas`. The team chose browser-native `window.print()` with CSS `@media print` and `@page` rules. This was the right call — lower risk, no dependency weight, and the output satisfies the offline use requirement.

## Challenges

**Story 6.8 acceptance criteria didn't capture the full navigation use case.**
The AC for travel segment display specified "transport type, duration, and distance when relevant." The printed output correctly shows e.g. `Car 1h:31m 81km` — but omits the from/to location names. A user standing at a location needs to know the destination to enter into a navigation system. The story was technically complete as written, but the user need wasn't fully captured.

**Story 6.8 map doesn't render in browser print.**
The `TripDayPrintPage.tsx` fires `window.print()` after 800ms, but Leaflet renders to a canvas element — tile loading and canvas paint are not guaranteed to complete before the print dialog opens. The manual browser QA step in the completion notes did not catch this. The AC said "includes a map section" but didn't define what a passing map looks like in a printed artifact.

**`project-context.md` was absent for the entire epic.**
Every story file (6.1 through 6.8) contains the note: *"No `project-context.md` file was found in this repository."* Each story assembled its context from planning artifacts, prior story files, and current code. This adds friction to every story and increases the risk that implementation context is assembled inconsistently across stories.

**`_bmad/core/tasks/validate-workflow.xml` is missing.**
Several stories (6.3, 6.4, 6.6, 6.7, 6.8) noted that the BMAD validator task file was not present, so checklist validation could not be run through the expected task runner. Story quality was checked manually instead.

## Key Insights

1. **UX consistency work is also a bug-finding mechanism.** Forcing two implementations into alignment reveals hidden divergence. This is a non-obvious benefit of consistency refactors beyond just polish.

2. **AC completeness is the weak point for export/print stories.** Features can be "done" against their written criteria while still missing real user needs. For any story involving print or export output, the AC should specify what the rendered artifact must contain for the user's actual use case, not just that a section "is present."

3. **Manual print/export QA is a category the automated suite cannot replace.** Browser rendering, print layout, canvas capture timing, and PDF output quality require human eyes. These need to be explicit done-criteria, not informal notes.

4. **Code review is load-bearing, not optional.** 5 of 8 stories had real issues caught at review. The review step is where correctness is actually verified, not just where style is polished.

## Story 6.8 Defects (Open)

### 6.8-A: Travel segments missing from/to location names
**Symptom:** Printed travel segment shows `Car 1h:31m 81km` but not the origin or destination location. User cannot determine what to enter into a navigation system.
**Root cause:** `TripDayPrintDocument.tsx` renders transport/duration/distance but does not render the preceding and following activity's location name alongside the travel segment row. The data is present in the print payload.
**Fix:** In `TripDayPrintDocument.tsx`, render the from-location (preceding activity) and to-location (following activity) as part of the travel segment row.
**File:** `travelplan/src/components/features/trips/TripDayPrintDocument.tsx`
**Priority:** High

### 6.8-B: Map does not render in printed PDF
**Symptom:** The map section is blank or absent in the printed/saved PDF.
**Root cause:** Leaflet renders to a canvas element. `window.print()` fires after 800ms but tile loading and canvas paint are not guaranteed complete by then. Browser print does not reliably capture canvas content.
**Fix:** Replace the live Leaflet map section in `TripDayPrintDocument.tsx` with a static OpenStreetMap or Google Maps URL for the day's route — rendered as a printed link that can be tapped on mobile or typed on desktop before going offline.
**File:** `travelplan/src/components/features/trips/TripDayPrintDocument.tsx`
**Priority:** High
