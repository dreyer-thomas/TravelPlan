# Story 7.2: Trip Overview Redesign

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a trip planner,
I want the trip overview to match the approved design (photo hero, day-row list with per-day photo and mini coverage bar, simplified cost summary, gap alert),
so that the overview is visually consistent and the "what's set, what's open" signal is immediately visible.

## Acceptance Criteria

1. Given `mockups/trip-overview-day-detail.html` (Screen A) and `EXPERIENCE.md`'s Trip Overview component patterns, when the trip overview screen is rebuilt, then it shows the photo-hero header (title/date over a scrim, no duplicated stats), day-row list with square center-cropped day photos and mini coverage bars, a simplified "Kosten bisher" summary, the trip map preview, and the gap-alert card.
2. Given a day has no accommodation on record, when the day-row renders, then it shows the warn-treatment gap badge and an enlarged gap segment in its mini coverage bar, per `EXPERIENCE.md`'s State Patterns.
3. Given existing trip data (accommodations, day plans, costs), when the redesigned overview renders, then all existing functionality (open a day, edit trip, share trip, export/import) continues to work unchanged — this story is visual only.

### TripDayGanttBar redesign (read before starting Task 6)

`TripDayGanttBar` (`src/components/features/trips/TripDayGanttBar.tsx`) is shared between the Trip Overview's mini coverage bar (this story) and the Day Detail's full coverage bar (Story 7.3, not yet built). Three things currently block Screen A's mini coverage bar from being reproducible at all:

1. **Colors are hardcoded to the pre-redesign palette** (`ganttColors`, lines 11-15: `accommodation: "#1b3d73"` navy, `travel: "#f08a24"` orange, `planItem: "#1f5e3b"` dark green) — none of these match `DESIGN.md`'s `components.coverage-bar` tokens (`seg-stay: accent #4B6358`, `seg-activity: accent-2 #7C9483`, `seg-travel: travel-neutral #B9B2A0`).
2. **There is no "gap" segment kind at all.** `TripDayGanttSegment["kind"]` (`TripDayGanttSegments.ts:4`) is `"accommodation" | "planItem" | "travel"` only. Uncovered time is currently just... uncovered — the bar's white background shows through with no distinct rendered segment. `deriveCoverageSummary()` already computes exactly the gap spans needed (`gaps: TripDayGapSegment[]`, `TripDayGanttSegments.ts:152-163`) but nothing currently turns them into renderable bar segments; they're only used today to compute the `unplannedMinutes` number for the text caption.
3. **`TripTimeline.tsx` currently feeds the bar pre-merged, kind-collapsed data.** `deriveCoverageSummary(ganttSegments).merged` returns spans with `{startMinute, endMinute}` only — no `kind` — because `mergeGanttSpans()` (`TripDayGanttSegments.ts:114-138`) is a generic interval-merge that doesn't preserve per-segment type through overlaps. `TripTimeline.tsx:522-526` then maps every merged span to `kind: "planItem"` as a hardcoded placeholder, which is why today's compact bar renders as a single undifferentiated color block regardless of what's actually in the day — it was never wired up to show per-type color, and this story is what finally requires it to. Fix: pass the **raw, unmerged** `ganttSegments` array straight to `TripDayGanttBar` (each segment keeps its real `kind`), and separately append synthesized `{startMinute, endMinute, kind: "gap"}` entries built from `deriveCoverageSummary(ganttSegments).gaps`. `TripDayGanttBar`'s own sort/render loop (lines 19-26, 44-65) already handles arbitrary numbers of segments correctly — it does not require pre-merging.

The `default` (non-compact) variant is shared with wherever `TripDayGanttBar` is used outside `TripTimeline.tsx` — grep confirms `TripDayView.tsx` also renders a gantt bar today (full-size, for the Day Detail screen). Story 7.3 owns that screen's full redesign; this story's Task 6 only needs to (a) fix the shared color tokens (a straight, low-risk win regardless of which screen renders the bar) and (b) add the `"gap"` kind + `compact`-specific 5px/2px/3px-6px-hatch sizing. Do not attempt to pixel-match the `default` variant to Story 7.3's not-yet-written Day Detail spec — just don't leave it visually broken (same "falls back cleanly" standard Story 7.1 set for out-of-scope screens).

### Data-model gaps discovered (confirm before implementing, don't silently guess)

- **No per-day "place name" field.** The mockup's day-row sub-label (e.g., "Lissabon") and the gap-alert's `{place}` interpolation both assume a place name is available per day, but `TripDay` has no such field — only `note` (free text, already used for the day title fallback) and the accommodation's own `name`/`location.label`. Task 2/Task 5 specify falling back to accommodation location label or omitting the sub-label; this is a judgment call flagged for confirmation, not a hidden assumption.
- **No travel-segment cost field.** `TravelSegment` (`prisma/schema.prisma:151-170`) has no `costCents`. The mockup's 3-row cost breakdown card cannot be fully reproduced — Task 3 specifies omitting the "Fahrt & Transport" row rather than fabricating a placeholder.
- **No booked/planned distinction in the day-row stay pill.** The mockup's day-row accommodation slot only encodes "has a place" vs. "gap" — the existing booked/planned Chip distinction (`TripTimeline.tsx:357-370`, `renderAccommodationStatus`) has no home in the new pill. Task 2 flags this as a decision needing confirmation rather than a silent removal.

### Test/heading-level conflict (read before Task 1's title markup)

`test/tripTimelineFeedback.test.tsx:121` asserts `screen.getByRole("heading", { name: "Viewer Trip", level: 4 })`. The current implementation achieves this via MUI's default `variantMapping` for `variant="h4"` (which renders an actual `<h4>` element). Story 7.1 added a new custom typography variant, `display` (28px/900/-0.4px), specifically for titles like this one — but **custom MUI typography variants have no default `variantMapping` entry**, so simply switching `variant="h4"` → `variant="display"` without also setting `component="h4"` will silently change (or remove) the rendered heading level and break this test. Explicitly pass `component="h4"` alongside `variant="display"`.
