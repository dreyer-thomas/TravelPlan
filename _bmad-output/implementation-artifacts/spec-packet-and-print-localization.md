## Intent

**Problem:** DW-230. A user on the German dictionary reaches both offline artefacts through fully localised UI and gets English. The packet PDF's label pages hardcode `"DOCUMENT"`, `"DOCUMENT NOT INCLUDED"` and the degradation sentence (`packetPdf.ts:347,378,698`); the print sheet is 100% English literals plus `Intl.DateTimeFormat("en-US")` (`TripDayPrintDocument.tsx:100`). Story 9.2 refused to half-close this — the packet alone would leave the day's two offline artefacts in *different* languages.

**Approach:** Resolve the request's language from the existing `lang` cookie on the packet route and thread it into `buildDocumentPacket` through its options bag; make `TripDayPrintDocument` a normal `useI18n` consumer like every other client component in the tree. Both halves read the same two dictionaries. No new locale mechanism, no new dependency, no route-shape change.

## Boundaries & Constraints

**Always:**
- **English output stays byte-identical.** Every new `en.ts` value is the literal it replaces, character for character (including `Tonight's` with a real apostrophe, `↗`, `Day route`, `Plan item {position}`). This is the regression gate: the 33 existing `tripDayPrintDocument` assertions and the 4 `printDocuments` label assertions must pass *unchanged in expectation*, only re-wrapped where a provider is now required.
- **Reuse the keys that already exist.** Transport labels are `trips.travelSegment.transport.{car,ship,flight,walking,cycling}` (`en.ts:391-395`, `de.ts:376-380`) and the distance unit is `trips.travelSegment.kmSuffix` (`en.ts:390`, `de.ts:375`). Do not add a second spelling of either.
- **The locale reaches the route from `request.cookies`, not `next/headers`.** `sessionGuard.ts:11` is the house pattern and the route suites construct real `NextRequest`s with no async-storage context. Cookie name comes from `LANGUAGE_COOKIE_NAME`, value through `resolveLanguage` — never a raw string compare.
- **Every string drawn into the PDF goes through `toWinAnsiText`, and the heading also through `wrapText`.** Today the heading (`packetPdf.ts:347`) skips both and the degradation sentence (`:378`) skips the sanitiser — safe only because the literals are known ASCII. Once the text comes from a dictionary that is no longer true, and `StandardFonts.Helvetica` **throws at draw time** outside WinAnsi. This hardening is required, not optional.
- **The packet's label strings must survive `toWinAnsiText` unchanged in both dictionaries**, pinned by a test. German umlauts (`ä ö ü ß`) are inside the sanitiser's `\xA0-\xFF` range and pass; `…` and typographic quotes do not — so do not write them into a `packetLabel*` value.
- `buildDocumentPacket`'s new option is **optional and defaults to `DEFAULT_LANGUAGE`**, so every existing call site and unit test keeps its current output.
- `getPrintEntryLabel` / `collectTimelineDocuments` take the `Plan item N` fallback as a **required** caller-supplied function, keeping `printDocuments.ts` locale-free and its import graph unchanged (still no `"use client"` module below it — the packet route imports it).
- New keys live under the existing `trips.dayPrint.*` (sheet) and `trips.documents.*` (packet) namespaces, added in the same order to both dictionaries. `i18nDictionaries.test.ts`'s parity assertion stays green.

**Block If:**
- Nothing. Both dictionaries, the cookie, `resolveLanguage` and the provider all exist and were read out of the tree; DW-230 names both files and the intent names the mechanism.

**Never:**
- Do not add `Accept-Language` negotiation, a `[locale]` route segment, a `next.config` i18n block, a locale middleware, or a DB read for the language. The `lang` cookie is the app's single runtime source (`layout.tsx:18`) and this change does not get to widen that.
- Do not localise the packet's `content-disposition` file name. `toSafeSlug` output is deliberately ASCII and `tripDayDocumentPacketRoute.test.ts:399,624` pin it; a translated file name buys nothing and risks a header-safety regression.
- Do not change the packet's page geometry, budgets (`MAX_PACKET_*`), degradation shape, guard chain, error **codes**, or `apiError` **messages** — API messages are English by house convention (the `code` is the contract; clients translate it).
- Do not reformat `distanceKm`, times, or costs. Only the one `Intl.DateTimeFormat` locale argument changes. Number/decimal formatting is DW territory this change does not own.
- Do not weaken an existing assertion. Extending an exhaustive list is allowed; loosening a matcher to accommodate German is not — add a German case instead.
- Do not edit `_bmad-output/implementation-artifacts/deferred-work.md`. The orchestrator records resolution.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Packet, no `lang` cookie | Authenticated request, cookie absent | Label pages read `DOCUMENT` / `DOCUMENT NOT INCLUDED` and the English sentence — identical bytes to today | `resolveLanguage(undefined)` → `en` |
| Packet, `lang=de` | Authenticated request with `lang=de` | Label pages read `DOKUMENT` / `DOKUMENT NICHT ENTHALTEN` and the German sentence; page count, page sizes, order and file name unchanged | No error expected |
| Packet, `lang=fr` (unsupported) | Cookie carries an unknown code | Falls back to English; no throw | `resolveLanguage` returns `DEFAULT_LANGUAGE` |
| Packet, degradation in German | `lang=de` and one encrypted PDF among readable ones | `200`, all label-page groups present, the failing one carrying the German heading and sentence | Per-document `catch` unchanged |
| Packet, label-page fallback | The inner `catch`-of-the-`catch` fires | Placeholder entry/file names come from the same dictionary as the rest of the packet | Second line of defence, unchanged in shape |
| Sheet, English | Provider language `en` | Every string and the date (`Intl` `en-US`, e.g. `August 10, 2026`) identical to today's rendered output | No error expected |
| Sheet, German | Provider language `de` | `Tag 2`, `Tagesroute`, `Reiseverlauf`, `Unterkunft der Vornacht`, `Programmpunkt 1`, German appendix; date `10. August 2026` via `de-DE` | No error expected |
| Sheet, unknown transport type | `transportType` outside the five known | Raw `transportType` printed, as today — **not** a missing-key string | Membership check before `t()` |
| Sheet, no documents | Day with zero document rows | Output byte-identical to today in English: no document pages, no appendix | No error expected |

**Acceptance Criteria:**

- Given the English dictionary, when the day sheet renders and the packet is built, then every visible string and the formatted date are identical to the pre-change output, and the existing print-sheet and packet suites pass with no expectation rewritten.
- Given an authenticated request carrying `lang=de`, when the packet route answers, then the merged PDF's label pages are German while its page count, page sizes, document order, `content-type` and `content-disposition` are unchanged from the English packet for the same day.
- Given a user with the German dictionary active, when they open the day print page, then the heading, both section captions, the stay-kind labels, the transport and duration text, the appendix and the browser tab title are German and the date reads `10. August 2026` rather than `August 10, 2026`.
- Given a titleless, textless plan item, when it appears both as an itinerary card and as a packet label page in the same language, then both name it with that language's positional fallback and with the same number.
- Given a packet request with no `lang` cookie or an unsupported one, when it is served, then it is the English packet and nothing throws.
- Given any value under `trips.documents.packetLabel*` in either dictionary, when it is drawn into the packet, then it is WinAnsi-encodable and `drawText` cannot throw, and a value that is not is caught by the dictionary test rather than at runtime.
- Given `npm test`, `npx tsc --noEmit`, `npm run lint`, `npm run check:migrations` and `npm run audit:check`, when they run after the change, then the recorded baselines hold with no new advisory, no new `src/` type error, and no increase in lint problems.

## Design Notes

**Why the locale is threaded, not inferred.** The app has exactly one runtime source of language — the non-`httpOnly` `lang` cookie written by `provider.tsx:32`, `login/route.ts:76-84` and `users/me/language/route.ts:56-64`. `User.preferredLanguage` exists in Prisma but is only ever *projected into* that cookie; nothing renders from it. Reading the cookie on the packet route therefore gives the same answer the menu item the user just clicked was rendered with, which is the whole complaint in DW-230.

**Why `src/i18n/request.ts` rather than calling `getServerT()`.** `next/headers` `cookies()` does work inside a route handler, but the packet route's suite builds a bare `NextRequest` and invokes `GET` directly — there is no request async-storage for `cookies()` to read, so the German case would be untestable at route level. Every other per-request read in this codebase (`sessionGuard.ts:11`, the CSRF guards) goes through `request.cookies`; this follows them.

**Why `printDocuments.ts` stays locale-free.** It is imported by both a `"use client"` component and a Node route handler, and its docblock makes that import graph an explicit constraint. A caller-supplied `(position: number) => string` keeps the module a pure traversal and makes the two callers visibly agree on the wording, and being *required* rather than defaulted is what makes the compiler name every call site — a default is precisely how one of the two would silently keep the old string.

> **Corrected during review.** This note originally justified the shape by claiming that handing the module a `t` or a `Language` would drag `@/i18n` and its two dictionaries into a client bundle. That cost does not exist: the `"use client"` component calling it imports `@/i18n` directly two lines away, and `src/i18n/provider.tsx` already imports `dictionaries` into every client bundle in the app. The decision stands on the reasons above; the bundle argument was wrong and is struck rather than quietly deleted, because the next reader deciding whether the constraint still binds needs to know it was checked.

**Why the sanitiser hardening is not optional.** `drawLabelPage:347` currently passes its heading as a one-element array with neither `toWinAnsiText` nor `wrapText`, and `:378` wraps but does not sanitise. Both are safe today only because the literals are hand-written ASCII sitting well inside 483pt. A dictionary value is neither guaranteed. German is fine on both counts — `DOKUMENT NICHT ENTHALTEN` is WinAnsi and short — so the hardening buys nothing *today* and everything on the next language added, which is exactly when nobody will re-read this function.

**The one thing to measure rather than assume** is the PDF text extraction in `documentPacketPdf.test.ts`. pdf-lib encodes `drawText` through the font's `encodeText`, which yields a hex string, and it does not flate-encode content streams — so scanning the saved bytes for `<…>` runs and latin1-decoding them should surface the label text. Prove that helper finds `DOCUMENT` in an English packet *first*; only then assert German with it. The fallback stated in the task is not a lesser test, it is a narrower one, and saying which was used matters more than which it is.
