## Intent

**Problem:** Four write paths have a blast radius wider than the thing they were asked to change. The worst (`DW-194`, the ledger's only `high`): `PATCH { imageUrl: null }` on the day-image route cleans up one file by `fs.rm`-ing the whole day directory — which is the parent of every stay/activity photo and every Story 9.1 ticket PDF on that day. One click destroys them all while touching no row, so the chips keep rendering and every one 404s. Alongside it: a post-commit unlink failure reports "removal failed" for a row that is already gone (`DW-195`), two concurrent overwrite imports of one trip interleave into one directory (`DW-86`), and a create-new import restores a foreign `/uploads/trips/<other-id>/…` URL that renders another user's photo (`DW-88`).

**Approach:** Narrow each action to what it owns. Delete the day image's own file (resolved from the previous URL, which the repository must start returning) instead of the tree; make post-commit filesystem failures log-and-continue through one shared helper; serialise overwrite imports per trip with an exclusive-`mkdir` sentinel; null foreign upload URLs on create-new and report the count.

## Boundaries & Constraints

**Always:**
- `DW-86`'s and `DW-88`'s recorded ledger decisions are the specification — implement them, do not re-derive them.
- Delete files, never directory trees, on any path whose stated job is one file. "Delete the directory but only when it is empty" is forbidden: emptiness is a race and the directory is legitimately non-empty whenever the day has any stay or activity media.
- The AC1 regression test is written first and observed **failing at baseline**, then fixed. A version of this story shipping without a test that failed beforehand has demonstrated nothing.
- `updateTripDayImageForUser`'s writer clause (`trip: { OR: [{ userId }, { members: … CONTRIBUTOR }] }`) is Story 5.13's and must not be disturbed while the `select` is widened. The route's `updated === null → not_found` semantics stay.
- `stashTripUploadDir`'s `ENOENT` swallow stays — a photo-free trip has no directory. The lock goes *above* it.
- The four `removeManagedFile` copies are byte-identical by design. Fix all four together (or none): three fixed and one not makes behaviour depend on which media type the user deleted.

**Block If:**
- Nulling foreign create-new upload URLs (AC6) forces a change to any assertion **other than** `travelplan/test/tripRepo.test.ts:1982` and `:2187` — see the Design Note. More than those two means the rule is wrong, not the tests.
- `DW-86`'s or `DW-88`'s recorded decision turns out to be unworkable against the actual code. Say so and stop; do not silently substitute a different design.

**Never:** No new dependency, no migration, no schema change. No orphan sweeper (`DW-187`) and no import-transaction rework (`DW-188`) — this story is containment of existing mechanisms, not new ones. No change to the stored URL scheme. No change to `travelplan/src/app/api/trips/[id]/hero-image/route.ts` (it owns a flat file, not a tree).

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|---|---|---|---|
| Day image removed | Day has `imageUrl` = own `day.webp`, plus a stay photo and a stay document under `days/<dayId>/` | `200`; `day.webp` gone; stay photo and document **byte-identical** on disk | No error expected |
| Day image replaced with external URL | `PATCH { imageUrl: "https://cdn.example/x.jpg" }` | `200`; previous own `day.webp` gone; sibling media survives | No error expected |
| Day image replaced within the day dir | New URL starts with `/uploads/trips/<tripId>/days/<dayId>/` | `200`; no unlink attempted (POST already replaced the file) | No error expected |
| Previous day image file already absent | Row has `imageUrl`, file missing on disk | `200`, row updated | `ENOENT` returns quietly |
| Previous day image is a foreign/external URL | `imageUrl` = `/uploads/trips/<otherTrip>/hero.jpg` or `https://…` | `200`; **nothing unlinked** — the route owns no file there | No error expected |
| Post-commit unlink fails, any media route | Row delete committed, `fs.unlink` rejects `EACCES` | `2xx` with `{ deleted: true }`; row gone | Logged via `console.error`, not thrown |
| Second overwrite import, same trip | Lock dir already exists and is fresh | Repository throws `import_in_progress`; route answers `409` | No row written, no file written |
| Stale lock | Lock dir older than the staleness timeout | Reclaimed once, then acquired; import proceeds | Reclaim failure ⇒ `import_in_progress` |
| Create-new import, foreign v1 URL | `heroImageUrl` / day `imageUrl` = `/uploads/trips/<other>/…` | Stored as `null`; `droppedImageCount` incremented; warning names the count | No error expected |
| Create-new import, own-trip URL | URL's trip id equals the created trip's id | Restored verbatim, not counted | No error expected |
| Overwrite import, foreign v1 URL | Same URL, `strategy: "overwrite"` | **Unchanged** — kept verbatim, as today | No error expected |

- [x] Same file -- reclaim must be **atomic** and release must be **ownership-checked**. On `EEXIST`: `stat`; fresh ⇒ throw `Error("import_in_progress")`; stale ⇒ `fs.rename(lockDir, \`${lockDir}.stale-<nonce>\`)` **and then verify, by comparing `fs.stat().ino` against the `ino` of the directory that was stat'd as stale, that the thing moved aside is the thing that was stale**; on a mismatch rename it back (best effort) and throw `import_in_progress`. `fs.rename` alone is *not* sufficient and the claim that "exactly one reclaimer can win" is false: two callers can both `stat` the same stale lock, the first renames it aside, removes it, `mkdir`s and writes its holder, and only then does the second's rename execute — moving the **winner's fresh sentinel** aside and claiming the lock as well. Confirmed by execution: two concurrent acquires against one stale lock both returned a lock, which is DW-86's interleaving reached through the lock. The winner removes the renamed directory and retries the exclusive `mkdir` once; every loser throws `import_in_progress`. A retry failing with a **non-`EEXIST`** errno rethrows rather than being reported as `import_in_progress`, which would be a permanent false "another import is running". **An `ENOENT` from the reclaim `rename` is not a lost race either** — it means the stale holder's own release removed the sentinel between the `stat` and the `rename`, so there is now no lock at all and the caller must go on to retry the `mkdir`, exactly as the `stats === null` branch beside it already does for the same situation observed one step earlier. Reporting `import_in_progress` there answers `409 another import is running` when none is. `releaseTripImportLock` reads the `holder` nonce and removes the directory **only if it still matches its own**, so a holder whose lock was reclaimed never deletes the reclaimer's. -- AC5, AC8
- [x] Same file -- refresh the sentinel's `mtime` (`fs.utimes`, ignoring failures) on a 60-second `setInterval` that is `unref()`'d and cleared by the release, so `IMPORT_LOCK_STALE_MS` means "the process is gone" rather than "the import is slow". ## Design Notes

### `DW-194`'s stated fix rests on a false premise — and so does AC7

The ledger says *"the route already knows the previous `imageUrl`"*. **It does not.** `updateTripDayImageForUser` (`tripRepo.ts:1075`) looks the day up with `select: { id: true }`, issues a raw `UPDATE`, then re-reads the **new** row. The previous URL is never captured. Widening that `select` is a repository change, not a route-local one — this is the single most likely hour to lose.

The same class of error is in **AC7**, and it must be resolved before implementation rather than discovered during it. AC7 asserts "the seven existing v1 tests that pin that string pass unmodified". Two of them are create-new tests over `IMPORT_PAYLOAD`, whose `trip.id` is `"export-trip"`:

- `test/tripRepo.test.ts:1982` — *"imports nested data in create-new mode with deterministic day ordering"*
- `test/tripRepo.test.ts:2187` — *"keeps the v1 image strings when a backup carries no pooled photos"*

Both pin `/uploads/trips/export-trip/days/export-day-2/day.webp` **after a create-new import**, where the created row gets a fresh `cuid`. That URL is foreign by construction, so AC6 requires it nulled. AC6 and AC7 cannot both hold on those two assertions.

`DW-88`'s recorded decision governs — the story states twice that these decisions *are* the specification — and it is explicit: *"null any `/uploads/trips/<id>/...` URL whose trip id is not the trip being created … the v1 verbatim rule is narrowed to URLs that still resolve."* Reading `<id>` as the *payload's* source trip id instead of the *created row's* id would defeat the entire fix, because `DW-88`'s harm case is precisely a URL matching the backup's own trip id (`"X's trip then stores /uploads/trips/<Y-trip-id>/hero.jpg and renders Y's image"`). `test/tripBackupRoundTrip.test.ts:842` corroborates: after a create-new v1 restore, `getTripUploadDir(newTripId)` does not exist at all, so such a URL cannot resolve.

So: AC6 governs, AC7's clause about the tests is a miscount, and exactly **two** assertions change from a verbatim string to `null`. The other five pins are unaffected and must stay green untouched — `:2333` (overwrite, rule not applied), `:550`/`:558` and `:668-669` (export-side, not import), `tripBackupRoundTrip.test.ts:831` (an *external* `https://` hero, which the rule never matches), and `tripImportSchemas.test.ts:376` (schema parse only). If a third assertion moves, the rule is wrong — see **Block If**.

### A URL prefix is not a containment check (AC8)

The first implementation guarded the new unlink with `storedUrl.startsWith("/uploads/trips/<tripId>/days/<dayId>/")`. That is not containment, and the review confirmed two ways through it by execution:

- `dayImageUpdateSchema` (`dayImageSchemas.ts:3-14`) accepts **any** string starting with `/uploads/` — no traversal check. So a writer can `PATCH` `…/days/<dayId>/../../../../../victim.txt`, which satisfies the prefix, and `resolveStoredMediaPath` + `path.join` then normalise it to `<mediaRoot>/victim.txt`. The next `PATCH { imageUrl: null }` unlinks it. The pre-diff route derived no path from a stored URL at all, so this capability would be **new**.
- Stay and activity media live **under** `days/<dayId>/` by construction (`uploadPaths.ts:94-123`), so a previous URL of `…/days/<dayId>/accommodations/<a>/img-stay.webp` satisfies the day prefix too, and unlinks a stay photo whose row survives. That is DW-194's exact symptom — a chip that renders and 404s — re-entered one file at a time.

Hence the rule is `path.dirname(resolvedPath) === path.resolve(allowedDir)`, with `allowedDir` built from ids by an `uploadPaths.ts` helper. One condition closes both holes: `..` normalises to a different parent, and a nested file has a deeper one. It is also uniform — every caller knows the exact directory its file belongs in — so the four media routes get the same rule instead of a trip-wide string test.

**But "the exact directory" is not derivable from the request (AC9).** The second attempt built `allowedDir` from `parsed.data.tripDayId`, the entry's *current* day, and that orphans files: `moveDayPlanItemToTripDay` (`dayPlanItemRepo.ts:660-698`) moves an activity between days with a bare `updateMany` of `tripDayId` — no file is moved and no URL is rewritten, deliberately, so that "everything attached to the activity travels with it for free". The stored URL therefore keeps the day the media was uploaded under. Confirmed by execution: upload → move → delete answered `200 { deleted: true }` with the row gone and the file still on disk, where the `/uploads/trips/<tripId>/` prefix test it replaced had removed it correctly. So the day segment comes from the stored URL via `readStoredMediaDayId`, validated with `isSafeMediaSegment`; everything else is composed from DB-sourced ids, and the comparison stays exact equality against a path built only from safe segments — so containment is preserved while the file is actually found.

**A silent refusal is not acceptable here.** The containment branch produces the same outcome as an `EACCES` — row committed, bytes orphaned — so it logs too. Iteration 2's version returned silently, which is how AC9's orphans left no trace anywhere: not in logs, not in tests, not in the suite's 2246 green assertions.

No `realpath` layer is added, and that is a **bounded** decision rather than a proof of safety. `fs.unlink` removes a symlink rather than its target, so the *final* component cannot escape; but `path.dirname(...) === path.resolve(allowedDir)` is lexical, so a symlinked **intermediate** directory would satisfy it while the unlink lands outside the tree. Nothing in the application creates symlinks under the media root, so this is an accepted residual risk, not a closed hole — say so in the comment rather than claiming there is no escape. (`resolveOwnedMediaPath` realpaths for precisely this reason; the serve route must, because it reads *through* the link.)

### "Does this look like ours?" is the wrong question, and four iterations proved it

Every spelling defect this story has produced has the same shape: a **string-shape test** decides whether a value names a file in our media tree, and a **resolved-path test** decides where that file is. When the two disagree, the shape test's "no" is a *silent exit* — no null on import, no unlink in cleanup, no log anywhere — so the disagreement is invisible.

The shape test has now been rewritten four times, and each rewrite was walked through by the next review:

| Iteration | Rule | Walked through by |
|---|---|---|
| 1 | `startsWith("/uploads/trips/<id>/")` | `//uploads/…`, nested media, `..` traversal |
| 2 | `startsWith("/uploads/")` on the raw string | `//uploads/…`, `/uploads//…` |
| 3 | leading slashes collapsed, then `startsWith("/uploads/")` | `uploads/…`, `/./uploads/…`, `/Uploads/…` |
| 4 | first non-empty, non-`.` segment `=== "uploads"` | `/x/../uploads/trips/<other>/hero.jpg` |

Iteration 4's rule is not a careless one — it was written specifically to survive iteration 3's three spellings, and it does. It fails because a `..` can *pop the segment in front of it*, so the first segment of the string is not the first segment of the path. Fixing that by resolving `..` before the test is exactly what this spec forbade in iteration 3, and correctly: `path.posix.normalize("/uploads/trips/../../../etc/passwd")` is not a media URL, which hands a traversal the very "nothing of ours here" exit the rule exists to deny it. Both directions are wrong, which is the signal that the question is wrong.

**The question that is decidable is "is this external?"** A value either parses as an absolute URL with a scheme or it does not; there is no fifth spelling of `https://`. So `isExternalMediaUrl` is the only shape test that survives, it is used *only* to let an external cover image out silently, and **everything else is treated as naming a path in our tree and sent to the resolved-path containment check** — which fails closed: not inside the directory you own means nulled (import) or refused-and-logged (cleanup). The escape case and the foreign-trip case stop being two rules with two exit paths and become one rule with one.

This also removes the second parse. `readStoredMediaDayId` derives its day segment from `path.relative(getTripUploadDir(tripId), resolved)` rather than from a `split("/")` of the raw URL, so there is exactly one authority on what a stored URL names — `resolveStoredMediaPath` — and every structural question is asked of *its answer*. A second parse is how iteration 4's `readStoredMediaDayId` came to disagree with its own module about three spellings; a rule that cannot be spelled around cannot drift from a rule that is not asked.

### Why not the summary grid

### Lock shape

```ts
export const IMPORT_LOCK_STALE_MS = 15 * 60 * 1000; // "the process is gone", given the mtime refresh
```
There is **no existing lock or `EEXIST` idiom anywhere in `src/`** to mirror; every `fs.mkdir` in the codebase is `{ recursive: true }`, which never fails on an existing directory and is therefore useless as a sentinel. The lock dir is a sibling of the trip dir under the trips root, like the existing `.import-<ts>-<rand>` stash, and does not collide with it lexically (`.import-l…` vs `.import-<digit>…`).

Acquire before the transaction, not before `stashTripUploadDir`: acquiring at the stash would let both imports commit their rows and only then serialise, leaving the loser to unwind a committed import.

Three properties the first implementation got wrong, each of which re-opens DW-86 or invents a new hole:

1. **The key must be a DB-verified, owned trip id.** `targetTripId` is validated only as `z.string().trim().min(1)` (`tripImportSchemas.ts:834`) and is interpolated straight into a path. The review confirmed by execution that `targetTripId: "../../../../probe-escape/x"` gets `fs.mkdir` — and then a `finally` `fs.rm(…, { recursive: true, force: true })` — on a directory **outside** the media root, reachable by any authenticated user with a parseable backup and no trip ownership at all. Resolving the id through `findFirst({ where: { id, userId } })` before locking fixes that and, at the same time, stops `409 import_in_progress` from being a discriminator for "an import of a trip you cannot see is running".
2. **Reclaim must be atomic.** `stat` → `rm -rf` → `mkdir` lets two callers that both read the same stale `stat` both succeed, because the second's `rm` removes the first's fresh sentinel. `fs.rename` is the atomic primitive: exactly one reclaimer can move the stale directory aside, and everyone else loses. Release must also be ownership-checked via a nonce, or a slow original holder's `finally` deletes the reclaimer's lock and opens the window for a third import.
3. **Staleness must be refreshed.** `mtime` set once at acquisition means the timeout measures *import duration*, not liveness — so a legitimate import near the 3 GB media ceiling has its lock stolen mid-flight by the very mechanism that exists to prevent two writers. A 60-second `fs.utimes` heartbeat, cleared on release, makes 15 minutes mean what the docblock claims it means.
