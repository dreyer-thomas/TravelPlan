# Story 7.3: Day Detail Redesign

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a trip planner,
I want the day view to match the approved design (photo hero, full coverage bar, timeline with neutral activity markers and photo strips, day map, bucket list, simplified day cost),
so that a single day's plan is visually consistent with the rest of the app and clearly shows what's covered vs. open.

## Acceptance Criteria

1. Given `mockups/trip-overview-day-detail.html` (Screen B) and `EXPERIENCE.md`'s Day Detail component patterns, when the day view is rebuilt, then it shows the day photo-hero, the full coverage bar (stay/activity/travel/gap segments in chronological order), the timeline (previous-night accommodation, activities, travel segments, current-night accommodation), the day map card, the bucket-list card, and the simplified "Kosten bisher · heute" cost card.
2. Given a generic day-plan-item activity node, when the timeline renders, then it shows the single neutral marker defined in `EXPERIENCE.md` — never a per-activity icon, since no activity-type field exists in the data model and none should be introduced to support this pattern.
3. Given an accommodation or day-plan item has multiple uploaded photos, when its timeline card renders, then the photos show as a uniform-size, left-aligned, square, center-cropped, sharp-cornered strip along the bottom of the card, per `DESIGN.md`'s photo-strip rule.
4. Given existing day-view functionality (add/edit accommodation, add/edit day-plan item, travel segments, bucket-list add-to-day), when the redesigned day view renders, then all of it continues to work unchanged — this story is visual only.

### Coverage-bar axis deviation (read before Task 3 — this is the story's biggest spec-vs-reality conflict)

The mockup's Screen B coverage bar is drawn over an **08:00–22:00** axis with five tick labels. `TripDayGanttBar` renders over a fixed **00:00–24:00** domain (`left = start / 1440`, `TripDayGanttBar.tsx:55-56`), and that is not an implementation shortcut — it is load-bearing for the data:

- `buildStaySegments` (`TripDayGanttSegments.ts:53-72`) emits the previous night as `0 → checkOutTime` and the current night as `checkInTime → 1440`. On the mockup's own example day those are exactly the first and last segments of the bar. Clamping the domain to 08:00–22:00 would visually truncate both stays and, worse, would make the bar disagree with the `plannedMinutes`/`unplannedMinutes` caption right beside it, which `deriveCoverageSummary` computes against a 1440-minute day (`:151`).
- Real days have content outside 08:00–22:00 — a 23:30 arrival, an 06:00 flight. The mockup's window is a property of its one sample day, not a product rule. `EXPERIENCE.md`'s own component-pattern row describes the axis as "08:00–22:00 on Screen B" purely descriptively, while the binding requirement in the same row is that segments are "strictly chronological, proportional to real duration".

So: **keep the 24h domain, label the axis 00:00 / 06:00 / 12:00 / 18:00 / 24:00.** Everything else about the coverage panel (the panel chrome, the legend, the 16px/4px bar, the hatch, the four fixed colors) follows the mockup exactly. Record this in Dev Agent Record as a deliberate, reasoned deviation so a future reviewer doesn't read it as a miss — and do not "fix" it by clamping.

### The 16:00/10:00 default-time trap (read before Task 3's gap synthesis)

`TripDayView` defaults missing stay times before feeding the gantt: `defaultCheckInTime = "16:00"`, `defaultCheckOutTime = "10:00"`, applied through `resolveStayTime` at `:938`, `:953-955`, `:974`. `TripTimeline`'s overview builder does **not** do this — it passes `checkInTime ?? null` straight through (`TripTimeline.tsx:593-601`). Consequence: on this screen a stay with no times *does* produce accommodation segments (using the assumed times), so 7.2's guard condition "an accommodation exists but contributes no segment" cannot be detected the same way here.

Port the guard by its **intent**, not by copying the coverage-derived heuristic: branch on `!!currentStay && !currentStay.checkInTime && !currentStay.checkOutTime` (the raw fields, before `resolveStayTime`), not on whether segments came out empty. Same for the previous night if you extend the guard. Getting this wrong produces one of two visible bugs: hatching a day that has a booked place to sleep, or hiding a real gap behind an assumed 16:00 check-in. Task 9's test (c) exists specifically to pin this.

Separately: decide and document whether the stat-strip's check-in cell shows the assumed `16:00` or an em dash. Task 4 says em dash, and the reasoning matters — the gantt's defaults exist to give the bar something to draw, whereas a stat cell is read as a fact about the booking.

### Test/heading-level conflict (read before Task 2's title markup)

Around fourteen assertions in `test/tripDayViewLayout.test.tsx` locate the page via `screen.findByRole("heading", { name: "Day N", level: 5 })`. Today that works because the title is `<Typography variant="h5">` and MUI's default `variantMapping` renders a real `<h5>`. Story 7.1's custom `display` variant has **no `variantMapping` entry** (custom variants never do), so switching `variant="h5"` → `variant="display"` without also passing `component="h5"` silently renders a `<span>` and takes out the whole suite.
