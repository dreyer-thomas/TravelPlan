# Accessibility Review — TravelPlan

Reviewed: `DESIGN.md`, `EXPERIENCE.md`, and the two approved mockups (`direction-merged-light-cockpit-v10.html`, `additional-screens-trips-list-share-login.html`) in `_bmad-output/planning-artifacts/ux-designs/ux-TravelPlan-2026-07-27/`.

Bar used: the PRD/epics.md pragmatic baseline — no WCAG AA/AAA conformance claim, but "strong contrast, visible focus, full keyboard navigation, touch targets ≥ 44×44px, map views paired with text summaries" (epics.md line 82; prd.md §Accessibility Level, edit-history 2026-02-12).

## Overall verdict

Against the stated pragmatic baseline, the color system itself is in good shape — text-on-background contrast, warn-state contrast, and role-badge contrast all clear ~4.5–6.5:1 by calculation, and the spine is unusually disciplined about pairing color with icon+text for every gap state (satisfying the PRD's explicit "not color-only" requirement for gaps). The weak spots are elsewhere: the approved mockups' actual interactive-element CSS falls well short of the 44×44px floor almost everywhere (a stated requirement the spine itself repeats but never checks the mockups against), icons carry no accessible-name guidance beyond one inconsistent `aria-hidden` example, and photography — explicitly called out in both docs as semantically meaningful — has zero alt-text guidance anywhere. None of this rises to "actively harmful" for sighted mouse users, but the touch-target and icon-labeling gaps would materially hurt keyboard-only and touch users, which the baseline was meant to protect.

**Findings by severity:** 1 critical, 5 high, 5 medium, 2 low (13 total).

## Findings

- **critical** The `bucket-add` "+" affordance (`.bucket-add`, `width:24px; height:24px`) is the sole way to add a bucket-list idea into a day plan and is little more than half the required touch-target size in both dimensions (`.working/direction-merged-light-cockpit-v10.html` line ~589-603). This is the most-repeated, most consequential violation of the epics.md "touch targets ≥ 44×44px" floor in the whole set. *Fix:* keep the visual 24px glyph but expand the hit area to ≥44×44px via padding/transparent hit-slop, or wrap it in a button with `min-width/min-height: 44px`.

- **high** Nearly every button, input, and select in both mockups computes well under 44px tall: `.share-btn`/`.back-btn` (~36px), `.primary-btn` (~40px), `.secondary-btn` (~35px), `.auth-submit` (~40px), `.input`/`.field-block .input` (~38px), `.select` role-dropdown (~35px), `.auth-tab` (~31px) — all derived from their `padding` + `font-size` in `direction-merged-light-cockpit-v10.html` and `additional-screens-trips-list-share-login.html`. EXPERIENCE.md's Accessibility Floor states the 44×44px requirement but neither DESIGN.md nor EXPERIENCE.md flags that the approved v10 mockups don't meet it — the requirement and the approved visuals silently disagree. *Fix:* either bump interactive-element vertical padding system-wide (e.g. min `12px 20px` at current font sizes lands closer to 44px) or add an explicit note in EXPERIENCE.md that visual padding in the mockups is illustrative only and implementation must hit 44px via `min-height`/hit-area, not literal mockup CSS.

- **high** The Share Dialog's "Entfernen" (remove collaborator) action (`.remove-link`, `additional-screens-trips-list-share-login.html` line ~303-308) is a bare text link with no padding — smallest, least forgiving target in the set, and it performs a destructive/consequential action (revoking access). *Fix:* give it a padded button hit area (≥44×44px) even if it keeps a link-like visual style, same as bucket-add.

- **high** Photography carries no alt-text guidance anywhere in either document, despite the review brief's (and DESIGN.md's own) framing of photos as semantic content — "which trip, which day, which activity." All photo surfaces (`hero-photo`, `day-photo`, `tl-photo`, `trip-photo`) are implemented as CSS `background-image` on `<div>`s, not `<img>` elements, so there is no native alt mechanism at all; a real implementation must actively choose between `<img alt="...">`, `role="img" aria-label`, or marking them `alt=""`/decorative — none of which is specified. DESIGN.md even anticipates future user-uploaded "trip cover photos" (Components §hero-photo) without addressing how those get a text alternative. *Fix:* add a short "Photo alt-text" subsection to EXPERIENCE.md: hero/day/trip photos are decorative (`alt=""`) when the adjacent title text already names the same entity (day-row, trip-row, hero); `tl-photos`/photo-strip images inside a stay/activity card should get a real, generated alt (e.g. "Photo of {activity title}, image {n} of {total}") since they're the closest thing to unique content in the timeline.

- **high** Meaning-bearing icons have no accessible-name convention. Of ~20+ inline `<svg>` icons in the mockups (house/stay dot, car/travel dot, gap-alert triangle, "Keine Unterkunft" pill icon, trip-status checkmark/clock/box/triangle, share/back/primary-btn icons), only the neutral activity-dot (`<div class="tl-dot activity" aria-hidden="true">`) is explicitly marked decorative. Every other icon SVG has neither `aria-hidden="true"` nor a `<title>`/`aria-label`, so a screen reader may announce an unlabeled/empty graphic once per icon instance — noisy but not misleading, since all of them sit next to visible text per the "icon + text, never color alone" rule already in EXPERIENCE.md. The rule about *pairing* icon with text exists; the rule about *marking the icon itself decorative for AT* does not. *Fix:* add one line to EXPERIENCE.md's Accessibility Floor: "all status/meaning icons are decorative (`aria-hidden="true"`) because their meaning is always duplicated in adjacent visible text; icons that are the *only* carrier of information (none currently) must get a real `aria-label` instead."

- **medium** `ink-muted` (#8A8677) on `paper` (#F7F4EC) computes to ≈3.3:1, and on `card`/white to ≈3.65:1 — both below the ~4.5:1 body-text threshold, though above the ~3:1 large-text/UI-component floor. DESIGN.md correctly restricts ink-muted to "placeholder-level text... never used for anything the user must read to act," but the mockups do use it for the `coverage-axis` time labels (`08:00`, `12:00`, `16:00`, `20:00`, `22:00` — `direction-merged-light-cockpit-v10.html` line 303) at 10px font-size. Axis labels are small, genuinely informative (they anchor the whole Gantt-style coverage bar), and sit right at the edge of "must read to act" for anyone auditing a day's schedule. *Fix:* bump coverage-axis label color to `ink-soft` (#6B675C, ~4.8–5.6:1) — it's a one-line token swap and removes the only borderline-contrast text usage in the system.

- **medium** The hero-photo header zone (breadcrumb/kicker text, `rgba(255,255,255,.82–.92)` over a scrim that thins to 10–26% opacity at the top) has self-acknowledged, unverified contrast margin against real photography. The mockup's own rationale comment (lines 662-666) states the top-of-photo text is "still legible in the screenshot, but with noticeably less margin than the bottom title" after testing against one real photo (`hero-mountains.jpg`) — i.e. this was empirically tested against exactly one image, not proven safe in general, and DESIGN.md explicitly commits this treatment to *future, user-uploaded* trip cover photos where brightness/content can't be controlled at all. This is disclosed, not hidden, but the disclosure stops short of a hard rule. *Fix:* either add a minimum-scrim-opacity floor at the top stop (e.g. never below ~0.35) that guarantees a text-safe zone independent of photo content, or require a client-side average-luminance check on the top third of any user-uploaded hero photo to auto-darken the top scrim stop when needed.

- **medium** Coverage-bar/Gantt segments distinguish "stay" (`--accent` #4B6358) from "activity" (`--accent-2` #7C9483) by color/lightness alone (contrast between the two swatches is only ~2:1) with no pattern or texture difference — only the "gap" segment gets a hatch pattern per the system's own "color is never the sole signal" rule. The full Screen B bar has a text legend nearby, so it's recoverable there; the mini per-row bar on Screen A (`.day-row` / `.trip-row`) has **no legend and no visible text**, only a `title` attribute tooltip — which is not reliably exposed to touch users, keyboard-only users, or many screen readers. A user who can't distinguish sage-green from forest-green (or who can't hover) sees a bar with segments but no way to tell stay from activity at the row level. *Fix:* either add a compact inline legend/key once per screen for Screen A, or give travel/activity/stay segments distinct subtle patterns (e.g. thin diagonal ticks vs. solid) the way gap already gets a hatch — consistent with the system's own stated principle.

- **medium** EXPERIENCE.md's Interaction Primitives section explicitly and correctly flags that hover/focus/active/pressed states were not mocked ("Gap not covered by mockups... Implementation must author these per the Accessibility Floor below") and the Accessibility Floor repeats "Visible focus state required... exact visual not yet specified." This is good — the gap is acknowledged, not silent, which is exactly what the review brief asked to check for. But the guidance stops at "must author these" with no concrete starting point (no suggested focus-ring color/width/offset from the existing token set), and several containers in the mockups use `overflow: hidden` (`.browser`, arguably `.day-row`/`.card` via border-radius clipping) which can visually clip a focus ring on an edge-adjacent element if implementers aren't careful. *Fix:* add one concrete default to the Accessibility Floor — e.g. "default focus ring: 2px solid `{colors.accent}` with 2px offset, tested against `card`/`paper`/hero-photo backgrounds" — so implementers aren't inventing contrast-safe focus styling from zero, and flag the clipping risk on `.browser`/rounded containers specifically.

- **medium** Role badges (Owner/Contributor/Viewer) rely on color *and* text ("Eigentümer"/"Contributor"/"Viewer" is always the literal badge label per `additional-screens-trips-list-share-login.html` lines 290-301) — this is correctly not color-only. However, Owner uses the same warn/terracotta palette (`#8A5A2B` on `#F6ECE0`) as every gap/error state elsewhere in the system (day-row gap pill, gap-alert card, trip-status.gap pill). A colorblind or quickly-scanning user could plausibly misread "Owner" as a warning/problem state on first glance, since terracotta is otherwise a hard-reserved "something's wrong" signal per DESIGN.md's own Do's and Don'ts ("reserve warn exclusively for gap/open-item states — never as a decorative accent"). This is a semantic collision, not a contrast bug. *Fix:* give Owner a neutral/ink-toned badge instead of reusing warn, preserving warn exclusively for actual gaps as the system's own rule intends.

- **low** DESIGN.md's Do's and Don'ts already states the warn-pairing rule ("pair every warn-colored signal with an icon and short text label, not color alone") and the mockups follow it consistently for gap states (day-row gap pill, gap-alert card, trip-status.gap pill all have icon+text). No issue found here — noted for completeness since it was one of the six things explicitly asked about. No fix needed.

- **low** Map previews are consistently paired with a text caption (`.map-caption`, e.g. "5 Stationen · Kartenvorschau öffnen") per EXPERIENCE.md's Interaction Primitives section and epics.md FR26 — verified present on both the Route card (Screen A) and Tageskarte (Screen B). No issue found; flagged only to confirm the check was made.

- **low** The empty-bucket-list state is explicitly marked `[ASSUMPTION]` in EXPERIENCE.md's State Patterns table with a concrete recommended treatment ("no illustration, no separate empty-state component invented") rather than being silently unspecified — good practice, low risk as-is, but worth confirming in the next review pass as the doc itself already requests.
