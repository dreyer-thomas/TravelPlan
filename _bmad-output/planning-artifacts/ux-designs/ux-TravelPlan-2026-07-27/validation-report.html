TravelPlan — UX Design Validation Report

_bmad-output/planning-artifacts/ux-designs/ux-TravelPlan-2026-07-27/

The pair is internally consistent, decision-dense, and clearly derived from a real, well-documented discovery process (.memlog.md corroborates every major visual call). Where it applies, it applies cleanly: token references resolve, German copy strings match verbatim across both files and both mockups, and section shapes follow the canonical order. But the spine specifies only the "read/reconnaissance" half of the product — five view-oriented surfaces built from an already-mostly-planned demo trip — while the entire authoring half (create trip, add accommodation, edit a day plan, password reset, any form/button/input primitive, loading/error/empty states) is either unmocked or unmentioned. Combined with two incorrect PRD FR citations and two unresolvable {size}-style token placeholders, a downstream consumer can source-extract the viewing surfaces with confidence but has no contract at all for the editing surfaces that make up most of the PRD's functional requirements.

The accessibility reviewer shifts the picture further, and specifically toward the surfaces the rubric already flagged as thin. Against the PRD's own stated pragmatic baseline (44×44px touch targets, strong contrast, no color-only signaling), the color system holds up well — but the approved mockups' actual interactive-element CSS falls well under the 44px floor almost everywhere (the bucket-list "+" affordance is roughly half the required size in both dimensions), meaning-bearing icons carry no accessible-name convention beyond one inconsistent example, and photography that both documents themselves call semantically meaningful has zero alt-text guidance anywhere. None of this is unique to the accessibility lens — it lands squarely on the same unmocked-primitives and unspecified-states gaps the rubric found — but it adds a second, independent line of evidence that the spine's thin spots (Component coverage, State coverage) are exactly where real users would be hurt first.

Accessibility review

review-accessibility.md

Bar used: the PRD/epics.md pragmatic baseline — no WCAG AA/AAA conformance claim, but "strong contrast, visible focus, full keyboard navigation, touch targets ≥ 44×44px, map views paired with text summaries" (epics.md line 82; prd.md §Accessibility Level, edit-history 2026-02-12).

Against that baseline, the color system itself is in good shape — text-on-background contrast, warn-state contrast, and role-badge contrast all clear ~4.5–6.5:1 by calculation, and the spine is unusually disciplined about pairing color with icon+text for every gap state. The weak spots are elsewhere: the approved mockups' actual interactive-element CSS falls well short of the 44×44px floor almost everywhere (a stated requirement the spine itself repeats but never checks the mockups against), icons carry no accessible-name guidance beyond one inconsistent aria-hidden example, and photography — explicitly called out in both docs as semantically meaningful — has zero alt-text guidance anywhere. None of this rises to "actively harmful" for sighted mouse users, but the touch-target and icon-labeling gaps would materially hurt keyboard-only and touch users, which the baseline was meant to protect.

Findings by severity: 1 critical, 4 high, 5 medium, 3 low (13 total; the source file's own summary line states 5 high/2 low, but only 4 findings are tagged high and 3 tagged low in the enumerated list below — corrected here).

critical

The bucket-add "+" affordance is roughly half the required touch-target size

.working/direction-merged-light-cockpit-v10.html line ~589-603
.bucket-add (width:24px; height:24px) is the sole way to add a bucket-list idea into a day plan. This is the most-repeated, most consequential violation of the epics.md "touch targets ≥ 44×44px" floor in the whole set.
Fix: keep the visual 24px glyph but expand the hit area to ≥44×44px via padding/transparent hit-slop, or wrap it in a button with min-width/min-height: 44px.
high

Nearly every button, input, and select computes well under 44px tall

both mockup files — .share-btn, .primary-btn, .auth-submit, .input, .select, .auth-tab, etc.
.share-btn/.back-btn (~36px), .primary-btn (~40px), .secondary-btn (~35px), .auth-submit (~40px), .input (~38px), .select (~35px), .auth-tab (~31px). EXPERIENCE.md's Accessibility Floor states the 44×44px requirement but neither DESIGN.md nor EXPERIENCE.md flags that the approved v10 mockups don't meet it — the requirement and the approved visuals silently disagree.
Fix: either bump interactive-element vertical padding system-wide (e.g. min 12px 20px at current font sizes lands closer to 44px) or add an explicit note in EXPERIENCE.md that visual padding in the mockups is illustrative only and implementation must hit 44px via min-height/hit-area, not literal mockup CSS.
high

Share Dialog's "Entfernen" (remove collaborator) is a bare text link with no padding

additional-screens-trips-list-share-login.html line ~303-308
.remove-link is the smallest, least forgiving target in the set, and it performs a destructive/consequential action (revoking access).
Fix: give it a padded button hit area (≥44×44px) even if it keeps a link-like visual style, same as bucket-add.
high

Photography carries no alt-text guidance anywhere

hero-photo, day-photo, tl-photo, trip-photo — both mockups + DESIGN.md Components §hero-photo
Despite the review brief's (and DESIGN.md's own) framing of photos as semantic content — "which trip, which day, which activity" — all photo surfaces are CSS background-image on divs, not img elements, so there's no native alt mechanism at all. DESIGN.md even anticipates future user-uploaded "trip cover photos" without addressing text alternatives.
Fix: add a short "Photo alt-text" subsection to EXPERIENCE.md: hero/day/trip photos are decorative (alt="") when adjacent title text already names the same entity; tl-photos/photo-strip images inside a stay/activity card should get real, generated alt text (e.g. "Photo of {activity title}, image {n} of {total}").
high

Meaning-bearing icons have no accessible-name convention

~20+ inline <svg> icons across both mockups
Only the neutral activity-dot is explicitly marked decorative (aria-hidden="true"). Every other meaningful icon SVG has neither aria-hidden nor a title/aria-label — noisy but not misleading, since all sit next to visible text per the "icon + text, never color alone" rule already in EXPERIENCE.md. The rule about pairing icon with text exists; the rule about marking the icon itself decorative for AT does not.
Fix: add one line to EXPERIENCE.md's Accessibility Floor: all status/meaning icons are decorative (aria-hidden="true") because their meaning is always duplicated in adjacent visible text; icons that are the only carrier of information must get a real aria-label instead.
medium

ink-muted on paper/card falls below the ~4.5:1 body-text threshold, used for coverage-axis time labels

direction-merged-light-cockpit-v10.html line 303
ink-muted (#8A8677) on paper (#F7F4EC) computes to ≈3.3:1, on card/white to ≈3.65:1 — below body-text threshold though above the large-text/UI-component floor. DESIGN.md correctly restricts ink-muted to placeholder-level text, but the mockups use it for coverage-axis time labels (08:00, 12:00, etc.) at 10px, which anchor the whole Gantt-style coverage bar and sit at the edge of "must read to act."
Fix: bump coverage-axis label color to ink-soft (#6B675C, ~4.8–5.6:1) — a one-line token swap that removes the only borderline-contrast text usage in the system.
medium

Hero-photo header zone contrast is self-acknowledged but unverified beyond one test photo

mockup rationale comment lines 662-666
Breadcrumb/kicker text (rgba(255,255,255,.82–.92)) over a scrim thinning to 10–26% opacity at the top was tested against exactly one real photo (hero-mountains.jpg), not proven safe in general — and DESIGN.md commits this treatment to future, user-uploaded trip cover photos where brightness can't be controlled. Disclosed, not hidden, but the disclosure stops short of a hard rule.
Fix: add a minimum-scrim-opacity floor at the top stop (e.g. never below ~0.35), or require a client-side average-luminance check on uploaded hero photos to auto-darken the top scrim stop when needed.
medium

Stay vs. activity coverage-bar segments distinguished by color alone at row level, no legend

.day-row / .trip-row mini bars, Screen A
--accent vs. --accent-2 contrast is only ~2:1, with no pattern/texture difference (unlike the "gap" segment, which gets a hatch). The full Screen B bar has a text legend; the mini per-row bar on Screen A has no legend, only a title-attribute tooltip not reliably exposed to touch, keyboard-only, or screen-reader users.
Fix: add a compact inline legend/key once per screen for Screen A, or give travel/activity/stay segments distinct subtle patterns the way gap already gets a hatch.
medium

Focus-state guidance stops at "must author these," no concrete default; clipping risk on rounded containers

EXPERIENCE.md Interaction Primitives; Accessibility Floor
The gap is transparently acknowledged, not silent — good. But no suggested focus-ring color/width/offset exists, and several containers (.browser, arguably .day-row/.card via border-radius clipping) can visually clip a focus ring on an edge-adjacent element.
Fix: add one concrete default to the Accessibility Floor — e.g. "default focus ring: 2px solid {colors.accent} with 2px offset, tested against card/paper/hero-photo backgrounds" — and flag the clipping risk on .browser/rounded containers specifically.
medium

Owner role badge reuses the warn/terracotta palette otherwise hard-reserved for gap/error states

additional-screens-trips-list-share-login.html lines 290-301
Owner uses #8A5A2B on #F6ECE0, the same palette as every gap/error state elsewhere (day-row gap pill, gap-alert card, trip-status.gap pill). A colorblind or quickly-scanning user could misread "Owner" as a warning/problem state, since terracotta is otherwise a hard-reserved "something's wrong" signal per DESIGN.md's own Do's and Don'ts. Not color-only (text label always present) — this is a semantic collision, not a contrast bug.
Fix: give Owner a neutral/ink-toned badge instead of reusing warn, preserving warn exclusively for actual gaps as the system's own rule intends.
low

Warn-pairing rule (icon + text, never color alone) verified consistent — no issue

DESIGN.md Do's and Don'ts
Mockups follow the rule consistently for gap states. No fix needed; flagged for completeness since it was one of the six things explicitly asked about.
low

Map previews consistently paired with text caption — no issue

.map-caption, Screen A Route card and Screen B Tageskarte
Verified present per EXPERIENCE.md's Interaction Primitives and epics.md FR26. Flagged only to confirm the check was made.
low

Empty-bucket-list state is explicitly marked [ASSUMPTION] with a concrete recommended treatment

EXPERIENCE.md State Patterns table
"No illustration, no separate empty-state component invented" — good practice, low risk as-is, but worth confirming in the next review pass as the doc itself already requests.

Mechanical notes

  • No Mermaid diagrams appear in either spine file (unlike ux-design-specification.md, which has three) — not required, not a defect.

Pre-existing source inconsistency, not created by the UX spine, but the spine's citations inherited it silently.
